### Prompt

This is the owner's authorised check of the DEV_OS engine 1.13.0 on GitHub, after the engine's security audit. The
publish job holds the only write token and runs `publish-verify.mjs verify` on every bundle the work job hands it,
before anything is pushed or reviewed (PR-90). This task proves that six kinds of forged content are rejected by
`verify()` itself — offline, with no GitHub call and no push — so the proof never needs real credentials or a real
remote.

**Preconditions. HALT if any is false.**
- `node scripts/devos/fence-check.mjs docs/fences/T28.md` prints OK.
- `node -e "import('./scripts/devos/publish-verify.mjs').then(m => console.log(typeof m.verify))"` prints
  `function`.

**Steps.**

1. Create `tests/canary-bundle.test.ts`, one Vitest `describe` block, `canary: a forged bundle is rejected before
   any push or review`, with one `it` per scenario below (six `it`s). Each test:
   - Builds its own throwaway **bare** git repository under `fs.mkdtempSync` (a stand-in "remote"), reachable only
     as a `file://` path — no network, no `DEVOS_GIT_TOKEN`, no real GitHub remote.
   - Seeds it with one commit on `refs/heads/main` (any small tree) to stand for `--main-sha`.
   - Builds a second throwaway working repository, branches `task/T01` from that commit (`T01` is a real, landed,
     non-method row of `docs/PHASES.md`: reuse its task id so `verify()`'s own read of main's `docs/PHASES.md` and
     `devos.config.json` — both read from this repository's real files, not the fixture — finds a matching row),
     makes the one forged change the scenario names, commits it, and pushes `task/T01` to the bare "remote" so
     `verify()`'s `ls-remote`/fetch of the branch succeeds.
   - Writes a `git bundle create` of that one commit on `refs/heads/task/T01` to a temp file.
   - Calls the exported `verify({ task: "T01", attempt: 1, branch: "task/T01", "main-sha": <the main commit>,
     out: <a fresh temp dir>, bundle: <the bundle file>, remote: <the bare repo's file:// path>, builder: "true" })`
     directly (import it from `../scripts/devos/publish-verify.mjs`), inside a `try`/`catch` (it calls
     `process.exit(1)` on rejection, which Vitest should not treat as the test's own exit — stub `process.exit`
     for the call, or run it in a child process; pick whichever keeps the test simple and document the choice in
     the report).
   - Asserts the rejection: the call either throws, exits non-zero, or returns/records `{ ok: false }` with a
     `reasons` entry that names the kind this scenario forges (a verify-written `verify.json` under `out` is one
     way to read it back). Assert nothing was pushed: `refs/heads/task/T01` on the bare "remote" still points at
     the commit it had before the call.

   The six scenarios (each changes only the one thing named, on top of the `task/T01` branch):
   1. **A review file** — adds `docs/reviews/T99.md`.
   2. **The config** — changes one line of `devos.config.json`.
   3. **The fence** — adds `docs/fences/T99.md`.
   4. **A workflow** — adds `.github/workflows/evil.yml`.
   5. **A forged verdict and checks** — changes `docs/PHASES.md` (a verdict cell) **and** adds
      `.devos/ci-results.json`, in the same commit.
   6. **A link and a `.gitmodules`** — adds a symbolic link (`fs.symlinkSync`, any target) **and** a file named
      `.gitmodules`, in the same commit.

   Use only Node's built-ins (`node:child_process`, `node:fs`, `node:os`, `node:path`) and `vitest`. Add no
   dependency. No identifier uses a forbidden noun (CLAUDE.md, Vocabulary).
2. Create `docs/canary/T28.md` with exactly these two lines:

   ```
   # Canary T28

   Six forged bundles (a review file, the config and the fence, a workflow, a forged verdict and checks, a link and a `.gitmodules`), each rejected by `publish-verify.mjs verify` before any push or review.
   ```

3. Run `pnpm exec vitest run tests/canary-bundle.test.ts` and
   `TASK=T28 node scripts/devos/run-checks.mjs --strict`. Paste both full results in `docs/reports/T28.md`, and
   for each of the six scenarios the exact rejection reason `verify()` gave.

**STOP block.**
- **HALT** when: a precondition is false; a step needs a file outside `Paths`; a scenario's rejection reason does
  not name the forged kind (the test caught the wrong rejection, or none); `verify()` is found to push, write, or
  contact a network address in any of the six calls.
- **REDACT-AND-CONTINUE**: clean any log line showing a local temp path before it lands in the report; continue.

### Done when

1. `pnpm exec vitest run tests/canary-bundle.test.ts` passes, with exactly six tests, one per scenario, each
   asserting both the named rejection reason and that the bare "remote"'s `task/T01` ref did not move.
2. `docs/canary/T28.md` holds exactly the two lines of step 2.
3. `TASK=T28 node scripts/devos/run-checks.mjs --strict` exits 0.
4. `grep -c '^it(' tests/canary-bundle.test.ts` or the vitest run shows six `it`s, each named after one of the six
   scenarios; the report lists, for each, the `reasons` entry `verify()` returned.
5. `grep -n 'DEVOS_GIT_TOKEN\|github.com' tests/canary-bundle.test.ts` prints nothing: the test reaches no real
   remote.

### Tests

- `tests/canary-bundle.test.ts`, as step 1 (six cases, one per forged kind).

### Do NOT

- Push to, or read from, any real GitHub remote; use a real write token; run `git push` to anything but the
  throwaway bare repository the test itself creates.
- Change any file outside `Paths`, add a dependency, or make a network call.
- Assert only on a console message: each scenario must read `verify()`'s own result (its `reasons`, or the
  `verify.json` it writes under `out`) and the unmoved ref, not a printed line alone.
